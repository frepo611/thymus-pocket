# Utvecklardagbok - 2026-06-01

## Vad gjordes idag

### Stabiliserat login/logout mellan Web och BFF

Arbetet idag fokuserade på att få sessioner stabila mellan SSR-frontend och BFF.
Symptomet var att en ny sessionsfil skapades i BFF vid återkommande inloggningar.

Det visade sig vara två olika men relaterade saker:

1. Web-appen pekade initialt mot fel BFF-port i development.
2. Web-lagret saknade komplett cookie-brygga mellan browser och BFF i SSR-flödet.

Båda delarna åtgärdades.

### Konfigurationsfix för development

I Thymus.Web appsettings.Development.json ändrades BFF BaseUrl från localhost:5001 till localhost:5000.
Det tog bort anslutningsfelet där login misslyckade med connection refused.

### BFF: återanvänd session-id och hydrerad session

I BFF loginflödet infördes återanvändning av befintligt session-id från cookie när det finns.
Om cookie saknas skapas nytt session-id.

För säkerhet och robusthet:

- Session-id valideras som 64 hextecken.
- Cookies sparas först till temporär fil och flyttas sedan atomiskt till slutfil.
- Misslyckad inloggning raderar endast temporär fil, inte en tidigare fungerande sessionsfil.
- Session kan återskapas från fil om servern startas om (minnesdictionary återfylls vid behov).
- Logout rensar både dictionary och sessionsfil baserat på session-id.

### Web: cookie-brygga i SSR

Den viktigaste kompletteringen i Web var att hantera BFF-sessioncookien explicit i serverkoden.

BffApiClient gör nu följande vid login och logout:

1. Läser inkommande thymus_session från browserrequest.
2. Skickar den vidare i Cookie-headern till BFF.
3. Läser Set-Cookie från BFF-svar.
4. Skriver tillbaka thymus_session till browserns response-cookies.
5. Vid logout rensas cookien även lokalt i Web-svaret för säker cleanup.

Detta behövs eftersom Web i SSR agerar mellanhand.
Browsern pratar med Web-sajten, men BFF-cookien sätts av BFF-domänen och behöver därför speglas korrekt så att samma session-id lever vidare mellan requests.

## Cookie handling i detalj

### Översikt av kedjan

Requestkedjan i SSR-läge:

Browser -> Thymus.Web -> Thymus.Bff -> SMF

Cookiekedjan som krävs:

- Browser håller thymus_session för Web-värden.
- Web vidarebefordrar thymus_session till BFF vid API-anrop.
- BFF använder session-id för att hitta sessionsfil med SMF-cookies.
- BFF svarar med Set-Cookie när session etableras eller uppdateras.
- Web speglar tillbaka relevant cookie till browsern.

### Login, steg för steg

1. User postar loginformulär till Web.
2. Web anropar BFF login-endpoint.
3. Om browser redan har thymus_session skickas den till BFF.
4. BFF autentiserar mot SMF.
5. BFF sparar SMF-cookies i sessionsfil för session-id.
6. BFF returnerar Set-Cookie för thymus_session.
7. Web fångar Set-Cookie och skriver motsvarande cookie i browserresponse.
8. Browser använder samma thymus_session vid nästa request.

Effekt:
Samma session-id kan återanvändas och befintlig sessionsfil uppdateras i stället för att skapa en ny för varje login.

### Logout, steg för steg

1. User triggar logout i Web (nu via global knapp i MainLayout).
2. Web skickar befintlig thymus_session till BFF logout-endpoint.
3. BFF försöker logga ut mot SMF och tar bort lokal sessionsfil.
4. BFF rensar sessioncookie.
5. Web rensar även cookie i browserresponse.
6. Browser saknar därefter giltig session och behöver ny login.

### Varför nya sessionsfiler kunde uppstå

Nya filer uppstår när BFF inte får ett igenkännbart session-id i request.
Då skapas nytt id och därmed ny fil.

Vanliga orsaker:

- Fel BaseUrl/port så cookie inte går till rätt backend.
- Cookie skickas inte vidare från Web till BFF i SSR-mellanlagret.
- Cookie finns men motsvarande fil saknas eller valideras bort.
- Avsiktligt nytt inloggningsflöde efter logout.

## Thymus.Contracts – delat kontraktprojekt

DTOerna för HTTP-kommunikation mellan BFF och Web var duplicerade i två namnrymder:
`Thymus.Bff.Contracts` och `Thymus.Web.Services`.

Problemet: varje ny DTO (som `BoardDto`) behövde definieras på två ställen.

### Lösning

Skapade `src/Thymus.Contracts` – ett vanligt klassbibliotek utan ramverksberoenden.

Innehåller:

- `BoardDto`
- `ThreadSummaryDto`
- `PostDto`
- `ThreadDetailsDto`

BFF och Web refererar båda projektet.

Inom respektive projekt används `global using`-aliases för att slippa ändra befintliga imports:

```csharp
global using BoardDto = Thymus.Contracts.BoardDto;
global using ThreadSummaryDto = Thymus.Contracts.ThreadSummaryDto;
// ...
```

BFF:s `Dtos.cs` behåller BFF-interna typer (`LoginRequest`, `ReplyRequestDto`) som inte tillhör det delade kontraktet.

### Strukturen

```
src/
  Thymus.Contracts/     ← nytt, refereras av Bff och Web
    Dtos.cs
  Thymus.Bff/
    Contracts/Dtos.cs   ← behåller bara BFF-interna request-typer
  Thymus.Web/
    Services/ThreadSummaryDto.cs  ← global using-aliases mot Thymus.Contracts
```

## Framtida steg: PWA-migrering

### Intention

Slutmålet för Thymus.Web är en PWA (Progressive Web App) — installerbar, med offline-stöd.

### Varför inte nu

Nuvarande `Thymus.Web` är Blazor Server med `AddInteractiveServerComponents`.
Blazor Server kräver en aktiv SignalR-anslutning till servern för all interaktivitet.
Det är strukturellt oförenligt med offline-stöd och service workers.

SSR-specifika mönster används dessutom aktivt idag:

- `[SupplyParameterFromForm]` i login-komponenten
- Cookie-bryggan i `BffApiClient` (Web vidarebefordrar cookies till BFF som mellanhand)

### Rätt grund för PWA: Blazor WebAssembly

WASM-varianten kör helt i browsern, har inbyggd PWA-mall och fungerar väl med BFF-arkitekturen.
Browsern pratar direkt med BFF — ingen server-mellanhand behövs.

Konsekvenser av migrering:

- `Thymus.Web` byter SDK från `Microsoft.NET.Sdk.Web` till WASM-modellen
- Login-flödet görs om från SSR form-post till `HttpClient`-anrop mot BFF
- `BffApiClient` cookie-bryggan tas bort — browsern sköter cookies mot BFF direkt
- Service worker och manifest läggs till för offline/install-stöd

### När

Lämpligt tillfälle är när det nuvarande feature-setet (boards, trådvy, svar) är stabilt och verifierat.
Migrationen är en dedikerad omskrivning och görs renast i ett eget steg utan pågående feature-arbete.
