## CSRF-planering och implementering av trusted-caller-skydd

### Analys

Gick igenom hotmodellen för CSRF i arkitekturen. Konstaterade att BFF är internt bakom Web-lagret: webbläsaren pratar med Web-appen, Web-appen pratar server-side med BFF. Browsern har aldrig en session-cookie för BFF-origin, vilket gör klassisk CSRF mot BFF till en låg risk i nuläget.

Web-lagrets egna formulär (login, logout) är redan skyddade av `app.UseAntiforgery()` i `Thymus.Web/Program.cs`.

### Implementerat: Trusted-caller-kontroll

Lade till en defense-in-depth-spärr mellan Web och BFF med en intern delad hemlighet.

**BFF (`Program.cs`):**  
Middleware tidigt i pipelinen som nekar alla `/api`-anrop utan rätt header:
```csharp
app.Use(async (context, next) =>
{
    // Validates X-Thymus-Internal-Secret on all /api paths
    // Returns 403 if missing or wrong
});
```
Jämförelsen sker med `CryptographicOperations.FixedTimeEquals` för att undvika timing attacks.

**BffApiClient (`Thymus.Web`):**  
Alla anrop mot BFF sätter nu `X-Thymus-Internal-Secret`-headern automatiskt via `ForwardSessionCookieToBff`.

**Konfiguration:**  
Hemligheten läses från `InternalApi:SharedSecret` (BFF) resp. `Bff:InternalApiSharedSecret` (Web). Nuvarande värde i `appsettings.json` är en development-placeholder och ska bytas ut i produktion via user secrets eller miljövariabel.

**Prioritet 2 – Smoke test end-to-end:**  
Starta BFF + Web och verifiera manuellt att login, boards-listning och reply fungerar med den nya spärren aktiv.

**Prioritet 3 – Framtida BFF-CSRF (om arkitekturen ändras):**  
Om BFF senare blir browser-facing (t.ex. via WASM-frontend eller separat SPA) ska ett synkroniserings-token per session läggas till. Då utökas `SessionState` med en `CsrfToken`-property, `SessionHelpers` med `GenerateCsrfToken()`, och write-endpoints med `X-CSRF-Token`-validering. `BffApiClient` uppdateras parallellt för att hämta och vidarebefordra tokenen.
