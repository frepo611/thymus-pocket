# Utvecklardagbok 2026-05-22

## Mål

- Köra PoC mot SMF och få ett stabilt end-to-end-flöde.

## Vad som fungerade

1. PoC byggde direkt utan kompileringsfel.
2. Inloggning fungerar nu mot SMF.
3. Cookies och sessionsdata hämtas korrekt.
4. Flödet för unread/recent körs klart.
5. Programmet avslutar nu korrekt med exit code 0.

## Misslyckanden och felaktiga antaganden

1. Första körningen gav 404 vid login.
   - Fel antagande: att login-endpoint kunde anropas utan att följa exakt dispatcher-routning.
2. Nästa försök gav 403.
   - Fel antagande: att user/pass räcker för login-submit.
   - Verklighet: dynamiska hidden fields krävs från login-formen.
   - Vad är hidden fields? SMF genererar per session ett unikt par fält i login-formen:
     - Ett sessionsfält med ett slumpmässigt fältnamn (t.ex. `b38ef54`) vars värde är sessions-ID:t.
     - Ett CSRF-fält med ett annat slumpmässigt namn (t.ex. `bba07664f080`) vars värde är en engångsnyckel.
     - Dessa är `<input type="hidden">` i HTML och syns inte för användaren i webbläsaren.
   - Syftet: att förhindra att ett POST-anrop kan komma utifrån utan att ha besökt login-sidan först (CSRF-skydd).
   - Konsekvens för PoC: man måste alltid göra en GET mot `action=login`, läsa ut dessa fältnamn och värden ur DOM:en, och sedan inkludera dem i POST-anropet till `action=login2`. Utan dem svarar SMF 403.

## Upptäckt om SMF-dispatchern (index.php)

1. Dispatchern använder `action` som nyckel till en action-map (`action => [source-fil, funktion]`).
2. `action=login` visar login-sidan, medan `action=login2` hanterar submit.
3. Om `action` saknas styrs flödet via board/topic till standardvyer (board index, message index, display).
4. Okänd `action` går via fallback/hook-logik, annars 404.
5. Detta förklarar varför fel action gav 404, och varför rätt action + rätt hidden fields krävdes för att passera validering.

## Gjorda korrigeringar

1. Loginflödet hämtar login-sidan, extraherar form action + hidden inputs, och postar allt tillsammans med credentials.
